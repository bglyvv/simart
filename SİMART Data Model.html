By domain

Identity & access

  • family — the account; everything else hangs off it.
  • parent — email/password and the PIN that gates /analitika & /tənzimləmələr.
  • child — one row per profile (avatar, DOB, city) — a family can hold several.

Habits

  • habit_category — Fiziki / Zehni / Sosial, shared across families.
  • habit_task — the catalog of trackable tasks per category.
  • habit_completion — one row per child, per task, per day.

Content (YouTube)

  • playlist — synced from @Simartaz, audience tag merged in by hand.
  • video — never a file, just a youtube_video_id + title + duration.
  • watch_progress — per child, per video.

Focus mode

  • focus_session — one row per lock: when it started, until when, why.

Games & cognition

  • game — the six mini-games, each tagged with a cognitive axis.
  • game_result — one row per play; feeds the parent dashboard's radar chart.

Economy

  • xp_transaction — the XP ledger (see note 1).
  • reward / reward_redemption — league-shop catalog + parent-approved claims.
  • wallet_transaction / donation_campaign — real AZN, kept separate from XP.

Social

  • social_post — posted under an anonymized handle, never the child's name.
  • post_like — one row per child, per post liked.

Design notes

  1. XP is a ledger, not a counter. Every action that grants or spends XP — a habit completion, a game result, a reward redemption, a donation — writes one xp_transaction row instead of mutating a single xp field (which is what today's mock store does). Current balance is SUM(amount); history and "why did my XP change" come for free.
  2. No league table. League standing is a pure function of the XP balance — XP = 1000 × 2^(L−1), exactly the formula already in leagues.json — so it's computed at read time, not stored.
  3. source_type / source_id is a polymorphic reference, used on both ledgers (xp_transaction, wallet_transaction). One row can point at a habit completion, a game result, a redemption, or a donation_campaign — without a separate nullable FK column for every possible source. donation_campaign stays unconnected in the diagram for the same reason.
  4. Catalog vs. instance. habit_task, game, reward, donation_campaign, playlist and video describe what's possible; habit_completion, game_result, reward_redemption and watch_progress record what a specific child actually did.
  5. Matches the existing content contract. playlist and video map 1:1 onto the Playlist / PlaylistVideo shape frontend/src/lib/contentService.ts already returns, so GET /api/content/playlists becomes a straight read off these two tables joined with the backend/src/playlistMeta.ts audience mapping — no shape change on the frontend side.
